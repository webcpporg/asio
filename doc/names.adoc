[#asio-names]
== The names

asio's targets are native, emscripten, wasip2 and wasip3. The table below compares
native and browser interfaces; <<asio-capabilities>> specifies the WASIp2 and WASIp3
subsets. Native equivalents retain Boost type identity. Wasm uses types from
the shipped implementation, with browser-specific extensions where required:

[cols="3,3,5",options="header"]
|===
| Name | Native | Emscripten

| `webcpp::asio::io_context`
| An alias of `boost::asio::io_context`, with exactly its constructors and members.
| A derived context over the shipped scheduler and reactor, the reactor made at
  construction, and the run family composed with the limit on the handlers
  one turn runs.

| Executors, `post`, `dispatch`, `bind_executor`, completion tokens, `co_spawn`
| Boost.Asio's.
| The shipped Asio backend's corresponding types and operations.

| `webcpp::asio::steady_timer`, `system_timer`, `basic_waitable_timer`
| Aliases of Boost's.
| Aliases of the shipped backend's timers, in the reactor's timer queue.

| Promises and events as operations
| None: nothing of the browser exists.
| A JavaScript promise and an event source, each an Asio operation.

| WebSocket and HTTP clients
| Boost.Beast.
| webcpp's beast library: Beast's interfaces over the browser's `WebSocket`
  and `fetch`.

| `ip::tcp`, `ip::udp`: sockets, acceptor, `resolver`
| Aliases of Boost's.
| Class templates of asio's with Boost's interfaces: each operation of a
  socket or an acceptor completes with `operation_not_supported` unless a
  transport provides it, and the resolver completes with the entries the
  browser streams of webcpp's beast library accept.

| `ssl`: `context`, `stream_base`, `verify_*`, `host_name_verification`
| Aliases of Boost's, in `<webcpp/asio/ssl.hpp>`, which brings OpenSSL
  natively, so that `<webcpp/asio.hpp>` leaves it out.
| A record of the program's TLS settings, which only the browser streams of
  webcpp's beast library read.
|===

A program includes `<webcpp/asio.hpp>` or the corresponding individual headers
and uses `webcpp::asio::` for the Asio names, including `post`, `co_spawn`,
`use_awaitable` and `bind_executor`. On native targets these names resolve to
Boost, so existing native Boost consumers remain interoperable. Wasm executors
and tokens belong to the selected implementation; mixing them with independent
Boost.Asio types does not select a compatible backend. See
<<asio-distribution-customization>> for custom completion tokens and traits.

The WebAssembly io_context takes its options, `io_context_options`, as the last argument
of each of Boost's constructors: with none, with an allocator, which it
allocates its services and its objects' state with, and with Boost's hint of
the concurrency it will see, with or without an allocator, so that Boost's
idiom `+io_context io{1}+` compiles unchanged. Its one option,
`max_handlers_per_turn`, 100 by default, bounds the handlers one turn of
its run family runs on emscripten before it yields to the browser; 0 is
taken as 1. WASIp2/P3 currently accept the options without changing their loop.
The native Boost type has no browser turn options or `max_handlers_per_turn`
member. Select browser-specific configuration explicitly in portable source.

On emscripten, `/webcpp/asio//asio` also gives every program the
configuration Asio needs to build there, and the link flags of its
suspension variant (<<asio-building>>).
