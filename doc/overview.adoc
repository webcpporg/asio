[#asio-overview]
== Why asio

Boost.Asio is the ground of asynchronous {cpp}: Boost.Beast, Boost.Cobalt,
Boost.MySQL, Boost.Redis and many others are written on it, as templates
over its executors, its completion tokens and its stream concepts. WebCPP
preserves that programming model while adapting execution and I/O to the
deployment target. Native equivalents are Boost.Asio itself. On Wasm, an
explicitly shipped implementation provides the backend selected by configuration.

`webcpp::cobalt` and `webcpp::beast` share this selected Asio backend.
Cobalt supplies coroutine types and a compiled runner. Beast supplies HTTP
messages, parsers and serializers, stream-based protocol operations, and
explicit browser and WASI host adapters. A browser has no ordinary raw TCP
listener: its WebSocket and fetch APIs are separate host facilities with
their own security policy. A socket-based server example cannot become a
browser listener merely by changing its namespace.

WASI guest sockets instead use the SDK's pollable or waitable reactor support.
They still require runtime network grants. A program using only timers has
different prerequisites from one using TCP, TLS, threads or host HTTP. The
feature matrix and named application profiles keep those requirements separate.

The browser's asynchronous model reaches {cpp}. The web's APIs are
asynchronous: promises, events, streams. asio makes a promise and an event
source Asio operations: a JavaScript promise is awaitable with any
completion token, `co_await`, a callback or a Cobalt task, and an event
source is an operation that completes on the event, so that {cpp} writes the
web's programs in the web's own model, and in {cpp}'s.

Emscripten supplies the suspension mechanism through JSPI or Asyncify.
WebCPP adds browser configuration, a bounded turn and wakeups from browser
events. These are library features, not compiler flags that grant access to
facilities absent from the host.
