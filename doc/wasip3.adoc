[#asio-wasip3]
== Build and test a WASIp3 program

This how-to uses the same timer example as the native tutorial. The port also
provides TCP/UDP through its selected socket backend. Read <<asio-capabilities>> before
choosing a profile; it records the restrictions that still differ from native.

=== Prerequisites

Use Boost 1.92.0, wasi-sdk 34.0 and Wasmtime 50.0.1 for the configuration verified
here. The distributed Wasm backend records exact upstream inputs and corrections.
Updating it requires rerunning the maintainer importer and regression tests;
an application build uses the sources already shipped in the library.
WASIp3 and cooperative threads require runtime support; the previously installed
Wasmtime 47.0.3 could not load the SDK's cooperative-thread component.

Register `clang-wasip3` in `user-config.jam` as shown by the superproject's WASI
setup. Put the SDK in `.local/wasi-sdk`, or supply `-sWASI_SDK=/path/to/wasi-sdk`
when choosing the cooperative profile. It must be the same SDK as the compiler
registered for this toolset. Put the tested Wasmtime binary on `PATH`.

`/webcpp/asio//asio` selects the shipped WebCPP headers and compiles
`src/wasip3/waitable.cpp`. It validates the SDK's private descriptor ABI before
building that bridge. Neither B2 nor another consumer build patches Boost or
inserts a replacement Boost include tree. See <<asio-distribution>> for the
equivalent source contract outside B2.

=== Run without threads

From the superproject root, build and check the existing timer example:

[source,bash]
----
b2 -a toolset=clang-wasip3 variant=release threading=single \
  exception-handling=on \
  testing.launcher=tools/boost/asio-wasip3/run.sh \
  libs/asio/example//asio_quick_start.output
----

The example's source is in <<asio-quick-start>>. Expected output:

[listing]
----
include::{examples}/asio_quick_start.expected[]
----

Repeat with `exception-handling=off` to use the single-thread runtime without
{cpp} exceptions. The library keeps Boost's callback and error-code interfaces.
No JSPI or Asyncify flags are needed.

=== Run with cooperative threads

[source,bash]
----
b2 -a toolset=clang-wasip3 variant=release threading=multi \
  exception-handling=off \
  testing.launcher=tools/boost/asio-wasip3/run.sh \
  libs/asio/test//wasi_core_threads
----

The build selects `experimental-coop-threads` as its sysroot and adds `-pthread`
consistently to compilation and linking. It uses that sysroot's {cpp} configuration
and the matching SDK's common libc{plus}{plus} headers. This is an experimental SDK profile,
not a promise of CPU parallelism. In the tested SDK, requesting exceptions in
this profile fails at configuration with a message naming the missing runtime.

The test launcher is for local and CI verification: it enables WASIp3 asynchronous
components and cooperative-thread support, grants host network and name-lookup
access for the loopback tests, and bounds each guest's execution to 600 seconds.
The global lane also runs large finite document and Unicode workloads. Set
`WEBCPP_WASIP3_TEST_TIMEOUT` to a positive integer number of seconds to choose
another bound, for example `WEBCPP_WASIP3_TEST_TIMEOUT=15` for focused loopback
tests. Invalid or zero bounds fail before launch. Enabling a runtime feature
does not create threads in a single-thread binary. Production applications
should choose their own timeout and network capabilities.

=== Reproduce the local verification

Run the declared WASIp3 tests and examples with `-a`, then repeat for each
supported profile from <<asio-capabilities-config>>:

[source,bash]
----
b2 -a toolset=clang-wasip3 variant=release threading=single \
  exception-handling=on \
  testing.launcher=tools/boost/asio-wasip3/run.sh \
  libs/asio/test libs/asio/example

b2 -a toolset=clang-wasip3 variant=release threading=single \
  exception-handling=off \
  testing.launcher=tools/boost/asio-wasip3/run.sh \
  libs/asio/test libs/asio/example

b2 -a toolset=clang-wasip3 variant=release threading=multi \
  exception-handling=off \
  testing.launcher=tools/boost/asio-wasip3/run.sh \
  libs/asio/test libs/asio/test//wasi_core_threads libs/asio/example

python3 libs/asio/src/wasip3/verify.py --sdk .local/wasi-sdk
python3 tools/test/asio_wasip3_test.py
python3 tools/test/cobalt_wasip3_test.py
----

`wasi_core` exchanges real TCP and UDP traffic over ephemeral IPv4 loopback
ports, tests timer and socket cancellation, scatter/gather TCP, and TCP EOF.
`wasi_core_threads` adds a cross-thread post into a reactor with a pending timer
and two runners sharing a context. `wasi_contract` checks empty datagrams,
vectored UDP receive with datagram truncation, IPv6 numeric scopes, socket
option errors and resolver behavior. `wasi_coroutine` waits for a timer using
Boost.Asio's `co_spawn` and `awaitable` with result-based error handling.
The existing run-family and timer tests also run on WASIp3.
`wasi_udp_gather` and `capability_wasi/datagrams` check synchronous and asynchronous
multi-buffer sends and receives,
including complete sequences beyond 64 buffers, allocation routing, empty
datagrams, oversized input and release of storage before completion.

The SDK verifier checks the private ABI snapshot. The maintainer importers check
source hashes, and external consumers use a source snapshot with spaces in its
path and no cached replacement Boost headers. Unsupported SDK profiles fail
with diagnostics. Native controls use the same runtime test sources. These are local
commands; none starts a CI job.

=== Build a Cobalt application

Use `<library>/webcpp/cobalt//cobalt` in the application's B2 requirements,
`webcpp/cobalt/` headers and `webcpp::cobalt` names. The application supplies
`co_main`; the separately compiled runner omits unsupported process signals.
Cobalt's explicit source inventory also supports other build systems. The old
Asio target is a forwarding alias, not a second implementation.

Run the existing <<asio-cobalt-example,Cobalt timer example>>:

[source,bash]
----
b2 -a toolset=clang-wasip3 variant=release threading=single \
  exception-handling=on \
  testing.launcher=tools/boost/asio-wasip3/run.sh \
  libs/cobalt/example//asio_cobalt.output
----

The expected output and complete source are in the
link:{webcpp-libs}/cobalt/{webcpp-page}#cobalt-tutorial[Cobalt tutorial].

Repeat with `exception-handling=off`, or with `threading=multi` and
`exception-handling=off` for the cooperative runtime. The latter can also run
the explicit `libs/cobalt/test//cobalt_thread` test. The ordinary test target
includes `cobalt_wasi`, `cobalt_network_exceptions_on/off` and `cobalt_io`; they cover the
runner, both timer APIs, Asio TCP/UDP through `use_op`, Cobalt's own IP socket
wrappers, refused TCP connections, TCP/UDP cancellation, EOF and result-based
resolver behavior.

The `libs/cobalt/test//cobalt_wasip3` lane checks successful and unsuccessful
command completion with an exact-status driver. Put Wasmtime 50.0.1 on `PATH`,
or set `WASMTIME` to its executable for that driver. The SDK maps nonzero
coroutine returns to host status 1.

For TLS, add `/webcpp/asio//tls` and await Asio SSL operations with
`webcpp::cobalt::use_op`. The following public-target drivers check TLS 1.2/1.3,
trusted and rejected identities, malformed CA data, transfer cancellation and
clean, failed and cancelled shutdown:

[source,bash]
----
b2 -a toolset=clang-wasip3 variant=release libs/cobalt/test/tls//tls
----

The WASI client needs network capabilities but no CA filesystem
preopen. To use Cobalt's own `io::ssl::stream`, link the optional
`/webcpp/cobalt//cobalt_ssl` target. Its shipped implementation, trust configuration and
local test commands are described in <<asio-cobalt-ssl>>.

The underlying platform contracts are documented by
https://github.com/WebAssembly/wasi-sdk/blob/main/CoopThreading.md[wasi-sdk's cooperative-thread guide]
and the
https://github.com/bytecodealliance/wasmtime/releases/tag/v50.0.1[Wasmtime release used here].
